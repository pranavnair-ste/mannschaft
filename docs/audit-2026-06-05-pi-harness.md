Generated by an 8-dimension parallel review with two-lens adversarial verification per finding.

**41 confirmed** (12 high, 24 medium, 5 low), 6 rejected. Findings below are sorted by severity. Note several are the same root cause found from multiple dimensions (deduped at fix time).

## 1. [HIGH] improve runner failure on success path leaks live team (credit burn) and skips consolidation/teardown

- **Location:** `pi_harness/topology/coordinator.py:365-371`
- **Category:** resource-leak  ·  **Found by:** topology

**Problem:** On the success path, on_completion() calls self._improve_runner.run_for_completed_run(...) BEFORE consolidate() and teardown(), with no try/finally. run_for_completed_run explicitly raises ImproveError (runner.py:200-213 documents 'we never swallow it' and raises 'No events for run {run_id}'). If it raises, consolidate() and teardown() never execute: the tmux session keeps running, agents keep burning OpenAI/pi credit indefinitely, and the worktree is leaked. The CLI caller (cli.py:162) invokes coord.on_completion(handle) directly with no surrounding try/finally, so the exception propagates and the operator is left with a live, orphaned team.

**Suggested fix:** Wrap the improve/consolidate steps so teardown always runs: `try: self._improve_runner.run_for_completed_run(...); self.consolidate(handle) finally: self.teardown(handle)`. Teardown (which kills the tmux session and stops credit burn) must be in a finally regardless of whether the improve loop or consolidation succeeds.

## 2. [HIGH] Transient ClawTeamCLIError during polling escapes wait_for_completion, leaving team live and run un-finalized

- **Location:** `pi_harness/topology/coordinator.py:316-322`
- **Category:** resource-leak  ·  **Found by:** topology

**Problem:** Coordinator.wait_for_completion only catches ClawTeamTimeout and ClawTeamRunFailure. The underlying client.wait_for_completion polls via list_tasks(), which runs `clawteam ... task list` with check=True and raises ClawTeamCLIError (a RuntimeError) on any non-zero exit (client.py:105-106, 247). A transient CLI failure mid-poll (e.g. clawteam binary hiccup, lock, network) therefore propagates out of Coordinator.wait_for_completion uncaught. The code after it never runs: mark_run_status is never called (run stays 'running' forever in the dashboard) and the CLI never reaches on_completion (cli.py:162), so the team is never torn down and keeps burning credit.

**Suggested fix:** Either catch ClawTeamCLIError (or broaden to ClawTeamError base) in Coordinator.wait_for_completion and treat it as a failed run (mark_run_status failed + return a RunResult with the error), or have the CLI wrap launch->wait->on_completion in try/finally that always tears the team down. Also consider making the poll loop in client.wait_for_completion tolerant of transient list_tasks failures.

## 3. [HIGH] Team launched but never registered / never returned when create_task fails — orphaned live team

- **Location:** `pi_harness/topology/coordinator.py:188-242`
- **Category:** resource-leak  ·  **Found by:** topology

**Problem:** launch() launches the team (live, burning credit) at line 192, then seeds the DAG in a loop calling create_task (202-209) which uses check=True and raises ClawTeamCLIError on any failure (e.g. a malformed subject/owner, a blocked_by id ClawTeam rejects, or CLI error). If create_task raises, the exception propagates out of launch() BEFORE the RunHandle is built (211) and BEFORE register_run (229). The caller therefore gets no handle and the run was never registered, so there is no record to drive teardown — the team is live and orphaned, and the run/<id> worktree created at 176-181 is also leaked.

**Suggested fix:** Wrap everything after launch_team in a try/except that, on failure, kills the tmux session, cleans up the team, and removes the run worktree before re-raising. Alternatively build+register the RunHandle immediately after launch_team (before seeding tasks) so a finalizer always has something to tear down.

## 4. [HIGH] Non-detach launch has no teardown on Ctrl-C or unexpected exception -> live agents keep burning credit + leaked worktree

- **Location:** `pi_harness/cli.py:152-169`
- **Category:** resource-leak  ·  **Found by:** cli

**Problem:** After coord.launch() returns (cli.py:153), a real ClawTeam team is live in a tmux session with agents actively running and burning API credit. The CLI then calls coord.wait_for_completion() (line 161) followed by coord.on_completion() (line 162). on_completion() is the ONLY place that tears the team down (kill_tmux_session + cleanup_team + remove_run_worktree). But there is no try/finally and no KeyboardInterrupt/signal handling anywhere in cli.py. Two real paths skip teardown entirely: (1) the user presses Ctrl-C while wait_for_completion is blocked in time.sleep(poll_interval) -- KeyboardInterrupt propagates out, on_completion is never called, the tmux session and all agents stay alive indefinitely; (2) an unexpected exception from the poll loop. Coordinator.wait_for_completion (topology/coordinator.py:320) only narrows `except (ClawTeamTimeout, ClawTeamRunFailure)`; but the poll calls client.list_tasks (clawteam/client.py:331) which runs `clawteam ... task list` with check=True and raises ClawTeamCLIError(RuntimeError) on any non-zero exit (e.g. transient clawteam/daemon hiccup). ClawTeamCLIError is NOT a subclass of ClawTeamTimeout/ClawTeamRunFailure, so it propagates straight out of coord.wait_for_completion and out of cli.launch, again skipping on_completion. In both cases the team keeps running, agents keep calling the model, and the run/<id> worktree under clawteam_state_dir/run-worktrees/ is left behind. There is also no `stop`/`kill`/`teardown` CLI command (only launch/lint/decompose/serve/spec exist), so the user cannot recover except by manually running `tmux kill-session` and `clawteam team cleanup`.

**Suggested fix:** Wrap the launch+wait block in try/except/finally in cli.launch: on KeyboardInterrupt or any exception after a successful coord.launch(), call coord.on_completion(handle) (or at minimum coord.teardown(handle)) to kill the tmux session and clean up, then re-raise/exit non-zero. Also broaden Coordinator.wait_for_completion's except to ensure on_completion still runs on ClawTeamCLIError, and add a `pi-harness stop <run_id>`/teardown subcommand so detached or abandoned runs can be stopped.

## 5. [HIGH] --detach launches a live, credit-burning team with no way to ever stop it via the CLI

- **Location:** `pi_harness/cli.py:158-159`
- **Category:** resource-leak  ·  **Found by:** cli

**Problem:** With --detach, cli.launch returns immediately after coord.launch() (which has already spawned a live tmux team with running agents). on_completion / teardown is never scheduled. There is no `pi-harness stop`, `kill`, or `teardown` subcommand (the only commands are launch/lint/decompose/serve/spec). The only artifact handed back to the user is the run_id printed to stdout. If a detached run hangs, loops, or the user simply forgets it, the agents keep calling the model and burning credit forever, and the run/<id> worktree under clawteam_state_dir is never removed. ClawTeam's own `team cleanup` does NOT kill the tmux session (documented in client.py kill_tmux_session docstring), so even a knowledgeable user cannot fully stop it without manual tmux surgery.

**Suggested fix:** Add a `pi-harness stop <run_id>` (and/or `runs` list) subcommand that reloads the RunHandle/team_name (it is already persisted via register_run in the trajectory DB) and calls Coordinator.teardown(). Document in --detach help that the run must be stopped explicitly, and consider persisting the team_name -> run_id mapping where stop can read it.

## 6. [HIGH] SSRF: /settings/models/local-models fetches an arbitrary attacker-supplied URL

- **Location:** `pi_harness/api/routes/settings.py:81-98`
- **Category:** security  ·  **Found by:** api

**Problem:** GET /settings/models/local-models takes a `base_url` query parameter directly from the caller, appends '/models', and performs httpx.get(url) server-side with no validation of scheme, host, or port. This is a classic server-side request forgery primitive: the API process makes an arbitrary outbound HTTP GET to any host/port the caller names (cloud metadata endpoints like http://169.254.169.254/latest/meta-data, internal admin services, localhost-only ports, etc.). Because the call is fully unauthenticated, any local process or (with broadened CORS) a browser can use the harness as an SSRF proxy. The response body and error text are reflected back to the caller (`could not reach {url}: {exc}`), which can also leak internal connection errors / hostnames. Note httpx.get follows redirects by default, so even an allow-listed host could redirect into the internal network.

**Suggested fix:** Validate base_url: require http/https scheme, resolve the host and reject private/loopback/link-local/metadata IP ranges (or restrict to an operator-configured allowlist of local model server URLs). Disable redirect following (follow_redirects=False). Do not echo the raw exception/url back to the client.

## 7. [HIGH] SQLite store opens connections with no WAL, no busy_timeout, and rollback journal — concurrent agent writers + dashboard reader will throw 'database is locked'

- **Location:** `pi_harness/trajectory/store.py:86-93`
- **Category:** concurrency  ·  **Found by:** trajectory

**Problem:** _connect() is the single connection factory used by every read and write (sync write_event, query_events, query_runs, runs.register_run/mark_run_status/get_run/query_run_summaries). It calls sqlite3.connect(db_path) with NO PRAGMA journal_mode=WAL, NO PRAGMA busy_timeout, and the default isolation_level. The harness's real topology spawns one agent_wrapper subprocess per agent (see agent_wrapper.consume_stream -> write_event), all writing to the SAME db file concurrently, while the coordinator's wait_for_completion._capture writes task_transition events, AND the FastAPI WebSocket route (api/routes/ws.py) polls query_events + get_run every ~1s. I empirically confirmed Python's sqlite3 defaults on this box: journal_mode='delete' (rollback journal, so a reader's SHARED lock blocks writers and vice-versa) and busy_timeout=5000ms. Because the rollback journal serializes readers against writers, any read that runs longer than ~5s while writers contend (or vice-versa) raises sqlite3.OperationalError: database is locked. That exception is then swallowed (see the bare-except findings), so events are silently lost — the audit trail this module exists to provide is dropped exactly under the multi-agent load it is designed for.

**Suggested fix:** In _connect (and the aiosqlite path), immediately after connecting run `conn.execute('PRAGMA journal_mode=WAL')`, `conn.execute('PRAGMA busy_timeout=30000')`, and consider `PRAGMA synchronous=NORMAL`. WAL lets the API reader run concurrently with agent writers; busy_timeout makes brief writer contention block-and-retry instead of immediately erroring.

## 8. [HIGH] Read paths (get_run, query_run_summaries) run CREATE TABLE/INDEX DDL + commit on every call, taking a write lock for read-only dashboard polling

- **Location:** `pi_harness/trajectory/runs.py:170,186,59-71`
- **Category:** concurrency  ·  **Found by:** trajectory

**Problem:** get_run() (line 170) and query_run_summaries() (line 186) both call init_runs_table(path) at the top of every invocation. init_runs_table -> init_db (store.py:96) issues CREATE TABLE IF NOT EXISTS, three CREATE INDEX IF NOT EXISTS, a SELECT, possibly an INSERT, and conn.commit(); then init_runs_table itself runs another CREATE TABLE + commit(). DDL/commit acquire a RESERVED then EXCLUSIVE write lock. The WebSocket route (api/routes/ws.py:28,43) calls get_run on connect AND every poll loop (~1s), and the runs list/detail endpoints call query_run_summaries. So purely read-only dashboard traffic repeatedly grabs the write lock on the shared db, directly colliding with the agent_wrapper writer subprocesses and massively amplifying the 'database is locked' window. With WAL+busy_timeout absent (previous finding) this turns every dashboard refresh into a writer-vs-writer contention event.

**Suggested fix:** Do schema init ONCE at startup (init_db_from_config / app startup), not inside read functions. Make get_run/query_run_summaries/query_events pure readers that never run DDL or commit. If you must guarantee tables exist, guard with a process-level 'already initialized' flag instead of re-issuing DDL per call.

## 9. [HIGH] agent_wrapper.consume_stream swallows write_event failures with a bare `pass` (no logging) — locked-db or serialization failures silently destroy the audit trail

- **Location:** `pi_harness/agent_wrapper.py:114-118`
- **Category:** error-handling  ·  **Found by:** trajectory

**Problem:** This is the ONLY live-agent capture path (PiEventParser -> write_event, spawned per agent by the Coordinator). On any write_event exception it does `except Exception: pass` with no log call whatsoever. Given the no-WAL/no-busy_timeout concurrency above, the realistic exception here is sqlite3.OperationalError('database is locked') under multi-agent load — exactly when capture matters most. Because it is swallowed silently (not even log.warning, unlike capture.py which at least logs), there is zero operator signal that the trajectory for a run is incomplete. The dashboard and the improve/cost layers then compute over a partial event set and report confidently wrong numbers. A swallowed write here is permanent data loss of the run's observability data.

**Suggested fix:** At minimum log.exception/log.warning the dropped event with run_id/agent_id/step_id so partial trajectories are detectable. Better: combine with WAL+busy_timeout (so transient locks retry rather than fail) and add a bounded retry around write_event before giving up.

## 10. [HIGH] return inside finally swallows all exceptions from the capture path, hiding agent failures

- **Location:** `pi_harness/agent_wrapper.py:156-161`
- **Category:** error-handling  ·  **Found by:** agent-wrapper

**Problem:** run() wraps consume_stream() in try/finally and the finally block executes `return proc.wait()`. In Python, a return inside finally unconditionally discards any exception that is propagating out of the try block. If consume_stream() (or init_db, the PiEventParser, the tee write to a broken pipe, etc.) raises, the exception is silently dropped and run() returns proc.wait() as if nothing went wrong. Combined with the fact that consume_stream already swallows write_event errors (line 117-118), this means a wrapped agent can die or mis-capture while the wrapper reports a clean exit code. There is no logging of the swallowed exception, so the failure is invisible. The unit tests never call run() (they test _build_argv / consume_stream / _resolve_provider_model only), so this is completely unexercised.

**Suggested fix:** Do not return from finally. Use try/except to log+re-raise (or convert to a nonzero exit code), and put proc.wait()/cleanup in finally without a return: e.g. `try: consume_stream(...) finally: proc.stdout.close()` then `return proc.wait()` after, or catch and log the exception explicitly before returning a failure code.

## 11. [HIGH] Tactical-staleness 'recent runs' window is inverted, prematurely archiving live tactical knowledge

- **Location:** `pi_harness/corpus/prune.py:198-210`
- **Category:** data-loss  ·  **Found by:** corpus-spec-guards-improve

**Problem:** prune_by_staleness archives a tactical entry when its last_referenced_run_id is not in the most-recent-K runs. The function computes that window as recent_run_ids[-tactical_recent_k:] (the TAIL of the list), and its docstring states the caller must pass 'the most recent K run ids'. But the real caller (improve/runner.py) builds recent_run_ids from query_runs which returns runs newest-first (DESC, documented as 'ordered by latest event ts desc'). Taking the tail of a DESC-ordered list yields the OLDEST K runs, not the newest. Once the corpus has accumulated more than tactical_recent_k (default 50) runs, an entry referenced by the *most recent* run is treated as unreferenced and gets ARCHIVE'd, while ancient runs incorrectly keep entries alive. This silently destroys (archives, eventually deletes) freshly-used tactical knowledge.

**Suggested fix:** Make the ordering contract explicit and consistent: slice the head (recent_run_ids[:tactical_recent_k]) to match the DESC order the caller supplies, or have the caller pass runs oldest-last. Add a unit test feeding a DESC-ordered run list asserting an entry referenced by the newest run is NOT archived.

## 12. [HIGH] Unvalidated spec_id enables path traversal (arbitrary file read/write/delete) in CLI and HTTP spec routes

- **Location:** `pi_harness/spec/format.py:73-74`
- **Category:** security  ·  **Found by:** cross-cutting-safety

**Problem:** spec_path(spec_id) = spec_storage_dir() / f"{spec_id}.md" performs NO validation/sanitization of spec_id. Every consumer feeds an externally-supplied spec_id straight into this. On the CLI: `pi-harness spec rm '../../../../home/user/.ssh/authorized_keys'` resolves to spec_storage_dir()/'../../../../home/user/.ssh/authorized_keys.md' and is unlink()'d (spec_rm), `spec show` reads any '<path>.md', `spec new`/`spec edit` write/open any '<path>.md'. On the HTTP surface the same spec_id flows from URL path params into _load()/serialize_spec() in editor.py (GET/PUT /specs/{id}, lint/decompose/launch). serialize_spec() also does path.parent.mkdir(parents=True) so a traversal write can create directories outside the specs dir. The id is never constrained to the _SLUG_RE charset used when minting new ids.

**Suggested fix:** In spec_path(), reject any spec_id that is not a safe slug: `if not re.fullmatch(r'[A-Za-z0-9._-]+', spec_id) or spec_id in {'.','..'}: raise ValueError`. Additionally resolve the final path and assert result.resolve().parent == spec_storage_dir().resolve() before any read/write/unlink.

## 13. [MEDIUM] Failure detection is dead code: FAILURE_STATUSES is empty, so failed/stuck teams burn credit until timeout

- **Location:** `pi_harness/clawteam/client.py:41, 337-345`
- **Category:** resource-leak  ·  **Found by:** clawteam-git

**Problem:** FAILURE_STATUSES is defined as an empty frozenset(). wait_for_completion computes `failed = [t for t in tasks if t.get("status") in FAILURE_STATUSES]`, which is therefore ALWAYS empty, so the `ClawTeamRunFailure` branch can never fire. ClawTeam 0.2.x has a 'blocked' status (per the module's own comment on lines 36-39) that can be terminal in practice (a dependency that never completes, or an agent that gives up). Because 'blocked' is neither in TERMINAL_STATUSES ({'completed'}) nor in FAILURE_STATUSES, a team where one task is permanently blocked or an agent dies will never satisfy `all(... in TERMINAL_STATUSES)` and will never raise — it polls every 5s until the full `timeout` elapses. Until then every agent tmux pane keeps running and burning API credit. The ClawTeamRunFailure exception class and the entire failure-handling branch in Coordinator.wait_for_completion (which catches ClawTeamRunFailure) are unreachable, giving false confidence that failures are surfaced quickly.

**Suggested fix:** ClawTeam has no 'failed' status, so detect stalls another way: track per-task last-change timestamps and raise ClawTeamRunFailure if the board has made no forward progress for N poll intervals while not all-completed (a 'stuck/no-progress' deadline shorter than the hard timeout). At minimum, document that 'blocked' tasks are treated as still-running and ensure the hard timeout is set conservatively so credit burn is bounded.

## 14. [MEDIUM] Run worktree leaked if launch_team raises after worktree creation

- **Location:** `pi_harness/topology/coordinator.py:176-198`
- **Category:** resource-leak  ·  **Found by:** topology

**Problem:** In the default (isolated) path, launch() creates a run/<id> worktree+branch (create_run_worktree, 180) and then later calls install_template and launch_team (189-198). install_template writes a global template file at ~/.clawteam/templates and launch_team runs `clawteam launch` with check=True. If launch_team raises ClawTeamCLIError (bad template, clawteam error, repo not clean), the freshly-created worktree and run/<id> branch are never removed — they accumulate in clawteam_state_dir/run-worktrees and as branches in the user's real repo on every failed launch. This is the same class of repo-pollution the operator already flagged for the test-mock path, but it also bites real failed launches.

**Suggested fix:** Guard the post-worktree-creation steps with try/except that removes the worktree (git_workspace.remove_run_worktree) and deletes the run/<id> branch on failure before re-raising.

## 15. [MEDIUM] Consolidation merge conflicts are silently discarded; run reported as success

- **Location:** `pi_harness/topology/coordinator.py:369`
- **Category:** error-handling  ·  **Found by:** topology

**Problem:** consolidate() returns the list of agent names whose merge into the run branch conflicted (it deliberately uses check=False and records conflicts rather than force-resolving). But on_completion() calls self.consolidate(handle) and throws the return value away. The CLI then prints 'work is on branch <run_branch> - diff and merge when ready' (cli.py:165-166) and exits 0, with no indication that one or more agents' work was NOT merged. An operator who diffs/merges run_branch silently loses the conflicting agents' contributions, believing the run fully succeeded. This is a data-loss-of-work / misleading-success problem.

**Suggested fix:** Capture conflicts = self.consolidate(handle); surface them (store on the run row / RunResult and print a warning in the CLI like 'N agents had merge conflicts and were NOT consolidated: ...'). Do not report unqualified success when consolidation was partial.

## 16. [MEDIUM] Concurrent SQLite writers with no WAL/busy_timeout cause 'database is locked' and silent trajectory data loss

- **Location:** `pi_harness/trajectory/store.py:86-93`
- **Category:** concurrency  ·  **Found by:** topology

**Problem:** _connect() opens sqlite3.connect(db_path) with no busy_timeout PRAGMA and no WAL journal mode. During a run, multiple agent_wrapper subprocesses (one per pi pane) call write_event() concurrently (agent_wrapper.py:115) AND the Coordinator's wait_for_completion _capture callback writes task-transition events on every 5s poll (coordinator.py:308-312) — all against the same trajectory.db. With the default rollback journal and only the default 5s busy timeout, concurrent writers routinely raise sqlite3.OperationalError 'database is locked'. Both write sites swallow ALL exceptions silently (coordinator.py:311-312 `except Exception: pass`; agent_wrapper.py:117-118 `except Exception: pass`), so locked-DB failures drop trajectory events with no log. Lost events then cascade: run_for_completed_run raises ImproveError 'No events for run' when every event was dropped (runner.py:212-213), which triggers the critical teardown-skip bug above.

**Suggested fix:** In _connect, set `sqlite3.connect(db_path, timeout=30)` and execute `PRAGMA journal_mode=WAL;` and `PRAGMA busy_timeout=30000;` on init. At minimum, distinguish OperationalError 'database is locked' from real errors in the swallow sites and retry, and log dropped events instead of pass-ing silently.

## 17. [MEDIUM] Path traversal in `spec` subcommands: unvalidated spec_id deletes/overwrites files outside the specs directory

- **Location:** `pi_harness/cli.py:257-313`
- **Category:** data-loss  ·  **Found by:** cli

**Problem:** The spec_id argument to `spec new`, `spec show`, `spec rm`, and `spec edit` is interpolated directly into a filesystem path (`_specs_dir() / f"{spec_id}.md"`) with no slug/character validation, despite the help text claiming 'Slug (e.g. dark-mode-toggle)'. Because pathlib's `/` operator collapses `..` and absorbs absolute paths, a spec_id like `../../somefile` resolves outside ~/.pi-harness/specs/. Concrete impact: `spec rm ../../../notes/important --force` deletes ~/notes/important.md (target.unlink(), line 301); `spec new ../../../somedir/evil --force` overwrites an arbitrary .md anywhere the user can write (target.write_text, line 267); `spec edit ../../foo` opens an arbitrary path in $EDITOR (subprocess.run([editor, str(target)]), line 313). The .md suffix limits this to .md files, but it still escapes the intended sandbox and can destroy user files outside it.

**Suggested fix:** Validate spec_id against a strict slug pattern (e.g. ^[a-z0-9][a-z0-9-_]*$) at the top of each spec subcommand and reject anything containing '/', '..', or path separators; after constructing target, assert target.resolve().parent == _specs_dir().resolve() before any read/write/unlink/edit.

## 18. [MEDIUM] CLI launch tests only exercise --detach, hiding the wait/teardown path and any Coordinator.launch signature drift

- **Location:** `tests/test_cli_launch_flags.py:41-62`
- **Category:** error-handling  ·  **Found by:** cli

**Problem:** Every launch test (test_cli_launch_flags.py and the launch tests in test_cli.py) invokes the CLI with --detach and mocks the Coordinator with a bare MagicMock. Consequences: (1) The non-detach path that calls coord.wait_for_completion() + coord.on_completion() (cli.py:161-162) -- the only path that performs teardown -- is never tested, so the missing try/finally / Ctrl-C teardown gap (finding #1) is invisible to the suite. (2) coord is a bare MagicMock, so coord.launch(run_spec, in_place=..., keep_alive=...) accepts ANY signature; a future signature change to Coordinator.launch would pass tests while breaking the real wiring. The tests only assert the kwargs they themselves pass, not that the real Coordinator accepts them. **Suggested fix:** Add a non-detach launch test that asserts coord.on_completion(handle) is called even when coord.wait_for_completion raises (KeyboardInterrupt and a generic exception), and that teardown is invoked. Use a spec'd mock (MagicMock(spec=Coordinator)) so signature drift on launch/wait_for_completion/on_completion is caught.

## 19. [MEDIUM] Unauthenticated /runs/{run_id}/branch launches a real multi-agent run (credit/resource burn, no auth)

- **Location:** `pi_harness/api/routes/runs.py:71-82`
- **Category:** resource-leak  ·  **Found by:** api

**Problem:** POST /runs/{run_id}/branch builds a Coordinator and calls coord.branch(run_id, step_id, overrides). Coordinator.branch (topology/coordinator.py:270-274) reloads the parent RunSpec, applies caller-supplied overrides, and calls self.launch(spec), which spins up a full ClawTeam team, spawns the 'pi' agent binary, creates git worktrees/branches in the real repo, and bills the model provider. The entire API has NO authentication of any kind (no Depends/Security/HTTPBearer anywhere in pi_harness/api). CORS is configured with allow_credentials=True and allow_methods=['*']. Any local process, any script, or a browser tab (if PI_HARNESS_FRONTEND_ORIGIN is ever broadened beyond localhost) can POST to this endpoint and kick off arbitrary, expensive, repo-mutating agent runs. The caller fully controls `overrides` (BranchRequest.overrides is an unconstrained dict[str, Any], models.py:73-75) which apply_overrides feeds into the spec (e.g. model_tier/topology/goal), so an attacker can also steer the run toward more expensive models.

**Suggested fix:** Gate all mutating endpoints (at minimum /runs/.../branch and /settings) behind an auth dependency (a per-install bearer token or local-only loopback token check). Validate/whitelist the keys allowed in `overrides` rather than accepting an arbitrary dict. Document that the server must never be bound to a non-loopback interface without auth.

## 20. [MEDIUM] WebSocket tailer blocks the event loop and does unbounded full re-reads per tick for non-terminal runs

- **Location:** `pi_harness/api/routes/ws.py:34-50`
- **Category:** resource-leak  ·  **Found by:** api

**Problem:** ws_run runs an infinite `while True` loop that, every poll interval (default 1.0s), calls the SYNCHRONOUS sqlite query_events(run_id=...) with NO limit (trajectory/store.py:146 uses blocking sqlite3, returns ALL events for the run). For any run that never reaches a terminal status (running, or any unexpected status value not in {succeeded,failed,cancelled}), the loop never exits on its own. Three problems compound: (1) query_events is a blocking sync DB call invoked directly inside the asyncio coroutine, so each tick stalls the entire FastAPI event loop for the duration of a growing full-table scan; (2) it reloads and re-instantiates DTOs for the full event list every second, with cost growing as events accumulate; (3) the loop only catches WebSocketDisconnect, so an exception from send_json on an abnormally-closed socket (or any error during query) escapes uncaught, and for stuck/never-terminal runs the connection (and its per-tick scans) persists indefinitely. Many concurrent WS clients on long-running runs can starve the loop / pin CPU.

**Suggested fix:** Run query_events in a thread (await run_in_threadpool / asyncio.to_thread) and pass a `since`/`limit` so each tick only fetches new rows, not the whole run. Add an overall connection/age cap and a max-poll-count guard so non-terminal runs eventually disconnect. Broaden the except to also handle send failures and DB errors, closing the socket cleanly.

## 21. [MEDIUM] get_run_detail and list_runs perform unbounded, N+1 full-table scans (DoS)

# Rejected (considered, dismissed by verifiers)

- **remove_run_worktree uses --force and check=False, silently destroying uncommitted/unmerged worktree work** (`pi_harness/clawteam/git_workspace.py:35-42`) — The finding's core premise — that `git worktree remove --force` "permanently deletes the only copy of the unmerged agent work" — is false. `git worktree remove --force` deletes a worktree's checked-out directory and its admin entry; it does NOT delete commits or branches, which live in the single shared .git object store of `repo`, not inside the worktree directory. So the run/<id> branch and every per-agent branch survive worktree removal.

The data-loss claim only holds if un-merged work existed solely as uncommitted/untracked files in the run worktree. The codebase shows it does not: consolidate() (coordinator.py:409-414) treats merge_workspace's non-zero exit as a git MERGE CONFLICT, and merge_workspace (client.py:150-172) is literally `clawteam workspace merge TEAM AGENT --target T` — merging an agent's *branch*. A merge conflict only occurs between committed histories, so the conflicting agent's work is committed on its agent branch (a ref `--force` cannot touch) and is recoverable. The docstring's claim ("the consolidated work lives on the branch") is therefore broadly correct: conflicting work survives on its agent branch even if not merged onto run/<id>.

Teardown ordering also undercuts the claim: cleanup_team ("free its worktrees", client.py:143-148) runs at coordinator.py:389 BEFORE remove_run_worktree at 392 — ClawTeam removes its own per-agent worktrees; remove_run_worktree is not the deletion path for them, and again cannot delete the underlying commits. On the failure/timeout path with keep_alive=False, snapshot_team (coordinator.py:374-376; client.py:174-185 snapshots "full team state") runs before teardown, so even that path is not a bare destroy.

The finding conflates "git refuses to remove a DIRTY worktree (uncommitted changes)" with "unmerged COMMITTED branches." --force is needed to cleanly remove the harness-owned run worktree regardless of incidental dirt; doing so does not destroy committed branch work. The only real residual is a minor observability nit: check=False could silently hide a *failed* worktree removal (leaving an orphan worktree dir / leftover state), which is robustness/cleanup-debt, not silent loss of user work — hence low severity, not the claimed high data-loss bug. | The code matches the finding (remove_run_worktree uses `git worktree remove --force` with check=False; consolidate() skips conflicting agents; the failure path tears down without consolidating when keep_alive is False), but the claimed data-loss mechanism does not hold on any realistic path. It rests on a wrong mental model of where agent work lives.

1) Route-level blocking of traversal. The endpoint is POST /corpus/entries/{entry_id}/restore using a BARE path param (corpus.py:131 `{entry_id}`, no `:path` converter). Starlette compiles a bare segment to the regex `[^/]+`, which does NOT match `/`. A literal `../../etc/passwd` (contains `/`) fails to match the route and returns 404 before restore_archived is ever called. A percent-encoded `..%2F..` is decoded to slashes by uvicorn into scope["path"] and likewise fails the `[^/]+` segment match. So the only ids that reach restore_archived are single path segments with no `/`, which cannot escape `root/archived/<classification>/` upward (e.g. id=".." yields `root/archived/<cls>/...md`, still inside root).

2) The headline "path traversal WRITE/unlink" claim is factually wrong. On a hit, restore_archived does `entry = parse_entry(archive_path)` then `writer.write_entry(entry, self.root, now)`. write_entry (writer.py:128-129) builds its target from `entry.classification` + `entry.id` taken from the PARSED FILE CONTENTS, NOT from the URL entry_id. So the URL id does not control where the active copy is written. The only op keyed to the (read) path is `archive_path.unlink()` — and that file must already exist AND parse as a valid `---`-delimited CorpusEntry (format.py parse_entry raises ValueError otherwise). So even a hypothetical traversal can at most read+delete a file that is already a well-formed corpus entry; it cannot write or unlink an arbitrary system file.

3) Read side is gated by .exists() + `.md` suffix + valid frontmatter, so arbitrary-file disclosure is implausible.

4) Deployment reality: the API binds 127.0.0.1 only (server.py:27,40), has no auth, and is a single-operator local harness dashboard. There is no untrusted remote actor in normal operation; the sole client is the operator's own localhost frontend. The operator can already write the filesystem directly.

5) Upstream id provenance: real entry.id values come from CorpusEntry.new() -> _hash_body() (format.py:79-88) producing `<record_type>-<12 hex>`, a strict slug. The improve-agent pipeline never emits `..`-laden ids, so _find_archived_entry_path is always called with safe slugs in practice.

Net: no concrete realistic call sequence reaches an out-of-root write/unlink. The route regex blocks slashes, the write target is content-derived not URL-derived, and the surface is localhost-only with no untrusted caller. This is a latent input-validation hygiene gap (worth adding a slug regex + resolve-inside-root assert as defense-in-depth), not a triggerable security bug. Blast radius in real-world harness operation is effectively nil, hence is_real=false and severity downgraded to low.
